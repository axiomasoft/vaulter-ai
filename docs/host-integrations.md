# Контракты подключаемого исполнителя и согласования

## H1. Граница пакетов

Первый потребитель — один агент Laravel AI с ключом провайдера на сервере. Его семь офисных операций и формат ответа определены в [контракте SDK](agent-sdk.md). Публичная CMS устанавливается автономно. Модули интеграции, настройки моделей, история запусков и предложения относятся к закрытой поставке. Edufy сохраняет разделение между сервисом AI и сервисом — владельцем файла. Фоновая задача переносит ссылку на контекст вызова и идентификатор команды; на старте каждой попытки заново разрешает субъект и ресурс.

| Интеграция | Что делает | Первая проверка |
| --- | --- | --- |
| Laravel AI | Один агент получает описание инструментов из офисного SDK. PHP-адаптер проверяет DTO, вызывает доменный обработчик и возвращает компактный результат модели. Ключ и авторизация сервиса не попадают в аргументы модели | Сначала подставной ответ модели, затем один настоящий вызов с тестовой учётной записью при наличии ключа. В обоих случаях подтверждается одно изменение и совпадает семантика квитанции |
| AgenTools, дополнительный Composer-пакет | Адаптер связывает доступные инструменты и вызов с существующими ToolPort и ToolDescriptorRegistry либо с Actions, если хост уже использует подтверждаемые действия. Публичные сигнатуры берём из выбранной ревизии AgenTools. Для долговременного процесса его ID действия сопоставляется с одним office command_id. Владельцем эффекта и квитанции остаётся редактор | Тот же пример из SDK проходит с тестовым исполнителем AgenTools и без модели. Если хост уже запросил проверяемое подтверждение для того же digest, интеграция использует его один раз согласно политике хоста |
| Сторонний процесс на Python | Авторизованный клиент вызывает HTTP-контракт SDK, сохраняет свой ключ повторной попытки, использует status и verify | После потери HTTP-ответа Python получает квитанцию прежней команды и читает достигнутую версию |
| Loqum, будущая интерактивная интеграция | Канал диалога передаёт окончательно распознанное поручение хосту. Хост связывает сессию с пользователем и выбирает агента. Закрытие диалога не отменяет уже подтверждённую запись | Эмулятор доставки одного финального сообщения дважды создаёт одно поручение. Возобновление сессии читает уже сохранённый исход. Незавершённая реплика не запускает запись |

Сейчас мы не устанавливаем Loqum в Vaulter. Первый срез работает через серверное обращение к SDK и через изолированного агента. Для будущей интеграции в рабочем окружении есть репозиторий `../loqum`, в нём `packages/js/sdk` и `services/gateway`. При появлении продуктовой задачи владелец канала адаптирует фактический API своего релиза. Формат сообщений Loqum, провайдеры речи и взаимодействие с микрофоном не закрепляются этим контрактом.

Существующие точки переиспользования в `../agentools` — `php/src/Contracts/ToolPort.php`, `php/src/Contracts/ToolDescriptorRegistry.php`, `php/src/Contracts/LlmPort.php`, примеры `examples/platform/confirmed-write` и `examples/platform/edufy-host`. Примеры дают основу для интеграционных тестов. Их синтетическое подтверждение не удостоверяет пользователя реального приложения. Прямую зависимость на `agentools/sdk` объявляет только соответствующий закрытый адаптер. Не создаём в Vaulter второй реестр моделей, биллинг или платформу оркестрации.

## H2. Конфигурирование и делегирование

Предлагаемая конфигурация по умолчанию в AI-пакете показана ниже. Это ключи нового пакета. Значение `office_model` — имя настроенного подключения хоста. Реальный секрет берётся из серверного хранилища при исполнении.

```php
return [
    'default_profile' => 'documents',
    'profiles' => [
        'documents' => [
            'executor' => 'laravel-ai',
            'provider_connection' => 'office_model',
            'commands' => ['text.replace_exact@1'],
            'approval' => 'required',
        ],
    ],
];
```

1. При сборке хоста доверенный service provider регистрирует исполнители, версионированные команды и профили. Повтор ключа команды с другой схемой или исполнителя с тем же именем — ошибка конфигурации. Для новой команды создаётся новая версия схемы и проверяемый пример.
2. На вызове хост выбирает профиль по контексту проекта и субъекту. В первом выпуске допустим один настроенный профиль. Позже Edufy может добавить профиль методиста, а FlexCrm — профиль для черновиков договоров. Инструкции пользователя или проекта дополняют задачу; их текст не даёт прав доступа.
3. Доступный набор вычисляется как пересечение установленных возможностей, разрешённых для профиля команд, политики проекта и текущих прав пользователя на конкретный узел. При отсутствии доступа результат одинаков для неизвестного и скрытого ресурса. Чтение, запись, просмотр квитанции и экспорт проверяются отдельно.
4. Хост задаёт внутреннее значение `approval = required` для обязательного согласования. Ответ `office.prepare` в этом режиме содержит `approval: "human"`. При автоматической политике обе стороны используют `automatic`. Дополнительное ограничение проекта/пользователя может потребовать подтверждения. Новый состав целей, другой digest, истечение срока либо отзыв прав делает старое согласие неприменимым. Окончание диалога, обрыв соединения и текстовое «да» сами по себе не являются подтверждением.
5. Метрики фиксируют профиль, тип инструмента, количество вызовов, размер результата, расход токенов, длительность и исход. В модель, метрики и обычный лог не передаются секреты, полный документ или текст другого пользователя. При разборе инцидента доступ к сохранённому diff и истории ограничивается действующими правами.

## H3. Предложения и интерфейс проверки

В первом UI списка предложений хост показывает документ и раздел, исходный форматированный фрагмент, предлагаемую замену, автора/инициатора, состояние и доступные действия. У предложения свой ID и digest. Владелец документа проверяет права в момент решения. При выдаче предложения и при решении хост проверяет актуальные права рецензента читать цель и согласовывать предложение. Исходный пользователь поручения остаётся субъектом исполнения. Непосредственно перед записью владелец заново проверяет право этого пользователя на изменение и действительность согласования, включая право рецензента, если хост требует его до фиксации. Согласование не передаёт пользователю возможности рецензента. В аудите раздельно сохраняются организация, область проекта, инициатор, субъект исполнения, рецензент, digest, ID команды, квитанция и затронутый фрагмент.

Решение имеет уникальный ключ предложения в его доверенной области. Хост в одной транзакции условно переводит его из ожидания в принятое либо отклонённое. При принятии закрепляет один предварительно сохранённый `command_id` и событие для очереди, при отклонении завершает предложение без исполнения. Повторные и конкурентные запросы читают выигравшее решение. Работник проверяет согласие, текущие права и предусловия и повторяет один commit под субъектом инициатора. Статус «рецензент принял» и статус «владелец сохранил» отображаются отдельно.

`office.status` доступен в исходных организации, области проекта и контексте инициатора. Чтобы увидеть исторический результат и diff, нужны актуальные права чтения соответствующего ресурса и истории. Просмотр решения другим рецензентом проходит через авторизованный UI хоста со своей проверкой прав на предложение, историю и фрагмент. Угадывание чужого ключа не выдаёт результат.

| Исходное состояние | Действие | Обязательный результат |
| --- | --- | --- |
| Предложение по «15 рабочих дней», в соседнем абзаце изменили реквизиты | Рецензент принимает предложение | Срок 30, оформление и реквизиты сохранены. Отображается подтверждённый результат |
| Целевой срок после подготовки уже равен 20 или абзац удалили | Принять исходное предложение | Исходное намерение конфликтует. Система предлагает заново прочитать цель. В документе остаётся актуальная правка |
| Два независимых предложения P и Q ожидают | Два пользователя одновременно принимают и отклоняют P | Одно конечное решение P. При сохранении прав оба видят одно решение, Q остаётся ожидающим. Допускается максимум одна содержательная запись по P |
| Предложение уже принято, ответ потерян | Повтор с прежним ключом | Доступный субъект получает ту же квитанцию. После утраты доступа нельзя выдать прежний diff |
| Обрыв браузера во время задания | Открыть новый клиент после выполнения | Хост восстанавливает состояние задания и квитанцию. Новая вкладка не инициирует повторный запуск |
| Один ученик видит урок, но не исходную книгу | Открыть превью или отправить его агенту | Содержимое и сниппеты закрытой книги отсутствуют. Группа преподавателей с нужным правом может открыть диапазон |

Минимальный собственный вариант поддерживает точную замену в одном текстовом фрагменте с однородным оформлением (`3.3`). Закрытые пакеты Client AI Toolkit, Compare и Import DOCX не используются. Range Comments, History Preview/Compare, Tracked Changes и DOCX Import/Export живут в `vaulter-editor-pro`, возобновляемый AI-чат — в `vaulter-ai`. Базовая CMS и итерация SDK развиваются независимо. ## H4. Как подключить внешний пакет и продолжить задание

Пример подключения для изолированного потребителя. Выбранная версия AgenTools предоставляет `ToolPort::call(string $tool, array $arguments, string $idempotencyKey): ToolExecutionResult` и `ToolDescriptorRegistry::descriptor(string $toolName): ?ToolDescriptor`. Последний контракт находит известное имя. Список разрешённых имён для конкретного запуска формирует хост. Профиль и доверенный контекст передаются адаптеру при создании задания.

| Что происходит | Что сохраняет хост или адаптер |
| --- | --- |
| Агент вызывает `office_prepare` для p42 | Разрешает имя в `office.prepare`, валидирует input по схеме SDK, вызывает обработчик от имени инициатора. Полученные `proposal_id`, digest, срок и требование согласования относятся к одному заданию |
| Хост принимает подтверждение P | Условно сохраняет решение из H3 и один `command_id`. При использовании AgenTools Actions связывает сохранённое действие, его idempotency key и офисное намерение. Повтор обработки того же действия восстанавливает это соответствие |
| Адаптер получает команду на фиксацию | Берёт сохранённый `command_id` из задания. Передаёт в SDK идентификатор ресурса, предложения, digest и этот ключ. Один ключ вызова инструмента для чтения и идентичность содержательной команды имеют разный срок жизни |
| Работник умер после запроса | Следующий работник восстанавливает исходную область и опрашивает `office.status`. После `committed` запрашивает `office.verify`. Хост связывает результат задания с квитанцией владельца и безопасной сводкой |
| Позже пользователь подключает своего агента | Доверенный provider хоста регистрирует исполнителя и сопоставление имён. Тот же текстовый тест выполняется через новый адаптер. Для добавления нового типа команды пакет предоставляет схему, проверку прав у владельца, обработчик, контрольную проверку и хотя бы один пример успеха и отказа |

Для первой версии достаточно одного сохранённого задания и одного документа. В итерации 7 черновик сложного поручения хранит ссылку на исходный ресурс и поколение, неизменяемые предложения, решения и исход публикации. У каждой публикации собственный ключ. Если в одном поручении несколько документов, хост ведёт независимые квитанции по ресурсам. После успеха первого и конфликта второго UI показывает частичный результат и требует перечитать второй. При повторе продолжается только незавершённая работа. Общий статус успеха выдаётся после проверки всех обещанных результатов.
