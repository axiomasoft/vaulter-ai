# Закрытый офисный SDK для агентов

Проект контракта v1, 20 ноября 2026. Первый потребитель — фоновый агент FlexCrm на Laravel AI. Второй — сервис Edufy с отдельным процессом исполнения. Цель первого релиза — довести до подтверждаемого результата два поручения: изменить конкретное условие договора и заполнить формулами выбранные строки книги. Работоспособность SDK проверяется без модели и открытого браузера, затем на том же контракте с реальным агентом. [Примеры обмена](../examples/office-sdk.json) · [Проверка соответствия схеме](../checks/verify-fixtures.py)

В FlexCms достаточно публичных пакетов и одиночного редактора. При отсутствии расширения Sheets каталог AI содержит только доступные текстовые команды. При отсутствии AI редактор полностью обслуживает действия пользователя. Отдельное подключение AgenTools или интерактивного сервиса Loqum определяется хостом.

## Транспорт и типы v1

Для PHP прикладной порт принимает доверенный контекст вызова и типизированные входные данные. Для отдельного процесса HTTP-адаптер предлагает `POST /api/vaulter-ai/v1/operations` с JSON и авторизацией хоста. Префикс можно настроить при установке. Одна операция на запрос, кодировка UTF-8. Каноническое имя операции содержит точку. Если провайдер модели ограничивает имена инструментов, адаптер задаёт обратимое соответствие, например `office_read → office.read`. PHP и HTTP вызывают один обработчик.

- Запрос содержит ровно `version: 1`, `operation: string`, `input: object`. Успех содержит `version`, `operation`, `ok: true`, `result`. Ошибка содержит `version`, `operation`, `ok: false`, `error`. Объекты закрыты. Версия определяется до диспетчеризации. Неразбираемое тело, отсутствие строкового имени операции или имя вне семи известных обрабатывает транспорт до диспетчеризации: HTTP 400, JSON `{"error":"invalid_request"}`, без эха имени. Такой ответ вне схемы офисного сообщения. При известном имени с целочисленной, но неподдерживаемой версией вернуть HTTP 400 и конверт сервера v1 с этой известной операцией и `unsupported_version`. Для известной операции v1 с некорректным input используется конверт `invalid_input`.
- Ниже перечислены обязательные поля. Суффикс `?` обозначает необязательное поле. Отсутствие и JSON null различаются. Null определён только для `next_cursor` и для рассчитанного значения пустой ячейки. Идентификаторы, ключи команд и токены чтения — непустые строки. Маркер позиции имеет отдельный тип Marker. Числовые значения книги представляются конечным JSON-числом; ошибка формулы — отдельное типизированное состояние.
- `Marker = {generation, position}` — пара целых неотрицательных чисел в безопасном целочисленном диапазоне JSON для v1. `position` упорядочен внутри одного ресурса и поколения. Для одиночного текста его отображаем на версию состояния, для живого текста — на подтверждённую последовательность журнала. Внешнюю ревизию движка книг сопоставляет адаптер. Восстановление открывает новое поколение. Предусловия, квитанции, история и результаты вычисления хранят полный контекст.
- `Page = {truncated: boolean, next_cursor: string|null}`. Для чтения одного ресурса курсор привязан к доверенной области, исходному селектору, поколению и позиции. Для поиска по нескольким ресурсам первая страница закрепляет снимок поискового индекса и полный порядок с уникальным ID в качестве последнего ключа сортировки. Курсор поиска связывает этот снимок, последнюю просмотренную запись и фильтры с областью вызывающего. Позднее добавление узла не сдвигает страницы этого поиска. На каждой странице права проверяются заново до выдачи метаданных. После удаления снимка или истечения срока курсора возвращается `cursor_expired`. `truncated = false` означает `next_cursor = null`. Если выдача не помещается даже после применения малой страницы, сервис сообщает `limit_exceeded` и предлагает сузить запрос. Частичную выборку нельзя молча принять за всю область записи. Лимиты строк, целей, полей, байтов и времени задаёт хост в пределах возможностей адаптера; тесты запускаются с закреплёнными лимитами.
- Владелец проверяет субъект и права непосредственно перед изменением и при каждой выдаче результатов. Субъект приходит из удостоверенного сеанса/задания. Переданные моделью имена пользователей, идентификатор организации или флаг согласия не предоставляют полномочий. Внешний клиент получает ограниченное по области и времени удостоверение своего хоста. Ключ LLM принадлежит процессу исполнителя.
- Фикстуры используют синтетические ID и квитанции. Начальный пример ставки срока имеет поколение 3 и позицию 27, книги — поколение 1 и позицию 11. Часы теста фиксируются на 20.11.2026 UTC до указанного срока действия предложения. Каждый сценарий начинается со своего исходного состояния.

## Семь операций

| Операция | Поля input | Поля успешного result |
| --- | --- | --- |
| `office.search` | `query: string`, `resource_type?: text/sheet`, `limit?: positive int`, `cursor?: string` | `items: [{resource_id,resource_type,title}]` и Page. Фильтры прав применяются до названий, совпадений, счётчиков и курсора |
| `office.read` | `resource_id, selector`, `limit?, cursor?, after_receipt?` | `marker: Marker, read_token, data` и Page. Маркер чтения фиксирует смысл и область выбранных данных. Стабильные ID листа, таблицы, блока, колонки получают через операции обнаружения ниже |
| `office.describe` | `resource_id, command` | `command, effect, input_schema, verification`. Версия команды входит в строку, например `text.replace_exact@1`. `effect = single_resource_write`; `input_schema` — закрытая схема аргументов выбранной команды. Оба первых профиля проверки перечислены ниже |
| `office.prepare` | `resource_id, command, read_token, arguments` | `proposal_id, digest, base: Marker, approval, summary, targets: string[], expires_at`. `approval = automatic/human`. `targets` — разрешённые ID блоков либо строк. В первом срезе полный список ограничен лимитом подготовки. `expires_at` — RFC 3339 UTC. Содержимое документа не меняется |
| `office.commit` | `resource_id, proposal_id, digest, command_id` | `command_id, state` и для `committed` также `receipt_id, marker`. `running` (HTTP 202) означает зарегистрированное намерение с ещё невыясненным исходом. `committed` (200) означает, что владелец зафиксировал эффект и обеспечил однозначное восстановление квитанции |
| `office.status` | `resource_id, command_id` | Для `running/committed` та же форма результата, что у commit. При окончательном отказе — `{command_id,state:"rejected",reason}`, где reason — безопасный стабильный код. Возврат сохранённого успешного исхода всегда требует текущего доступа |
| `office.verify` | `resource_id, receipt_id, mode`; `mode = at_commit/current` | `receipt_id, mode, outcome, marker, checks`. `outcome = passed/failed`; `checks = [{name,passed:boolean,actual}]`. При отставании проекции или расчёта возвращается `projection_pending` или `calculation_pending`; можно повторить чтение без повтора записи |

Выдача описаний ограничивается актуальными полномочиями; список кратких имён доступных команд предоставляет адаптер исполнителя при начале задания. Сервер закрепляет версию каталога для запуска. Модель запрашивает `office.describe` только для нужной команды. Регистрация новой версии не изменяет смысл уже подготовленного предложения. Сменившийся несовместимый профиль возвращает `schema_changed`, даже если отображаемый текст выглядит так же.

### Обнаружение и чтение

Для первого релиза закрытый дискриминируемый объект `selector` имеет четыре формы. Имена полей в каждой строке исчерпывающие.

| Селектор | Возвращаемая форма data |
| --- | --- |
| `{kind:"text_outline",query?}` | `{kind,blocks:[{block_id,path:string[],snippet}]}`. Оглавление и поиск под ограничением текущего документа. При поиске «срок» агент различает пункты 4.2 «Расчёты» и 7.1 «Претензии» |
| `{kind:"text_block",block_id}` | `{kind,block_id,segments:[{text,marks:string[]}]}`. Для v1 записи допустима одна непрерывная цель внутри одного текстового фрагмента с однородным поддерживаемым форматированием. Маркер чтения привязан также к исходным атрибутам, положению и контексту блока. В отображаемой сводке `marks` — имена; исходные атрибуты ссылки или иных marks обязаны сохраниться |
| `{kind:"sheet_catalog"}` | `{kind,tables:[{sheet_id,sheet_title,table_id,table_title,columns:[{column_id,title}]}]}`. Даёт адресуемые листы, таблицы и колонки с доступом пользователя |
| `{kind:"sheet_table",sheet_id,table_id,columns:string[],row_ids?:string[]}` | `{kind,sheet_id,table_id,rows:[{row_id,values:{column_id:scalar}}]}`. Ключи значений совпадают с доступными запрошенными колонками; scalar — строка, число, boolean или null. Для неподдерживаемой ячейки в этой первой команде подготовка возвращает `unsupported_content`. Развитие чтения произвольных диапазонов и агрегатов сохраняет версию старых селекторов |

Пользователь также может передать из UI разрешённую ссылку на документ или выделение. Сервис заново разрешает её в текущем хосте. Для книги с произвольными строками первой команде требуется таблица с устойчивыми идентификаторами строк. Если движок хранит только координаты, Sheets должен обеспечить такие ID в своей модели или отклонить неподдерживаемую операцию. Адрес C3 после вставки строки уже может означать другой товар.

Для выделения браузер сопоставляет выбранные строки с устойчивыми ID в данной книге и передаёт их хосту. Хост либо агент вызывает `office.read` с `selector.row_ids`. Поле принимает непустой список различных непустых ID в пределах лимита. Сервис возвращает строки в порядке таблицы, привязывает токен к области, указанным колонкам и всем выбранным ID. Скрытые политикой доступа и отсутствующие ID дают одинаковый `resource_unavailable` без частичного ответа. Свёрнутая в интерфейсе строка сохраняет свою идентичность и подчиняется той же политике доступа.

Токен отдельной страницы пригоден для чтения. Подготовка записи v1 требует, чтобы исходный ответ охватил всю область за один вызов. Последняя страница многостраничного результата тоже содержит лишь часть области. При превышении лимита агент получает `limit_exceeded` и может заново прочитать меньшую явно выбранную область. Для `current_rows` требуется токен полного чтения таблицы без `row_ids`, а также проверяемое право на весь состав. Фильтрованный токен для этой команды даёт `invalid_input`, отсутствие полномочий на всю таблицу даёт `resource_unavailable`. Команда `fixed_members` принимает как полное выделение по ID, так и полный результат чтения таблицы. При подготовке и фиксации проверяются именно выбранные строки.

`after_receipt` означает текущую выдачу не ранее позиции квитанции в том же поколении. Авторизация выполняется и при ожидании готовности, и перед передачей данных. Квитанция живого текста доступна после SQL commit. Если комната или проекция ещё догоняет журнал, чтение возвращает данные из подтверждённого состояния либо `projection_pending`. После восстановления старый маркер возвращает `generation_changed`. Точная историческая проверка использует `verify(at_commit)` с доступной сохранённой квитанцией и её доказательствами. Она может продолжать работать после восстановления, если у пользователя есть актуальное право на эту историю. Поздняя правка человека может законно привести к `verify(current).outcome = failed` при успешной проверке на момент фиксации. ## Команды содержимого

**Текст.** `text.replace_exact@1` принимает ровно `{block_id,expected,replacement}`. Идентификатор и ожидаемый фрагмент непустые. Пустая замена означает удаление. Текст для проверки берётся без нечёткого поиска, автокоррекции и подмены пробелов. Исходный фрагмент обязан иметь единственное совпадение внутри цели и поддерживаемую разметку. Неподдерживаемая структурная операция отклоняется до изменения. Для принятия равенства проверяются идентичность узла, выбранный текст, значимые соседние слова и исходная разметка. Чужая правка другого раздела не инвалидирует цель. Смена «рабочих» на «календарных» в целевом условии возвращает конфликт даже при неизменном числе 15. Проверка `text_and_marks` перечитывает от владельца замену и ожидаемые marks на зафиксированной версии, в том числе атрибуты, если они есть.

Правила цели v1 одинаковы для PHP-владельца и любого клиента ProseMirror/Tiptap:

- Цель — текстовый блок `paragraph`/`heading` с `attrs.blockId = block_id`, в том числе вложенный в список или цитату. Его текст — конкатенация text-узлов; каждый нетекстовый inline-лист (`hardBreak`, изображение и т. п.) даёт один символ U+FFFC. В `text_block` такой лист — отдельный сегмент `{text:"\uFFFC",marks:[]}`. Смещения считаются в кодовых единицах UTF-16, поэтому позиция ProseMirror равна `позиция блока + 1 + смещение`. Байты UTF-8 и code points для этого непригодны.
- Run — максимальный участок соседнего текста с одинаковым набором marks вместе с атрибутами. Сохранённый Tiptap JSON может содержать соседние text-узлы с одинаковыми marks; до поиска они объединяются, как это делает `Fragment.fromArray`.
- Совпадения `expected` считаются с перекрытием, от каждого начального смещения: `1-1` встречается в `1-1-1` дважды. Подходит только ровно одно совпадение, целиком лежащее в одном run. Требования к границам слов нет.
- Замена получает marks этого run вместе с атрибутами, например `link.href`. Соседние run и другие блоки не меняются.
- Контекст в v1 — весь целевой блок: тип, attrs, текст и marks с атрибутами. При commit он должен совпасть с блоком, закреплённым при prepare. Правка другого блока допустима.
- Отказы до записи: блок или фрагмент не найден, контекст блока изменился → `precondition_failed`. Больше одного совпадения, пустой `expected`, U+FFFC в аргументах или невалидный UTF → `invalid_input`. Совпадение пересекает границу run или лист, повторный `blockId`, неадресуемый тип блока → `unsupported_content`.
- `text_and_marks` проверяет сохранённый снимок квитанции (`at_commit`) или текущее состояние владельца (`current`). `text_exact.actual` — участок квитанции `[start_utf16, start_utf16 + length(replacement))` в этом состоянии. Проверка проходит, только если весь текст блока равен зафиксированному. `marks.actual` перечисляет имена marks этого участка. Проверка проходит, если каждый символ участка несёт ровно зафиксированные marks с атрибутами. Поэтому смена `href` проваливает `marks`, хотя имя `link` прежнее. При удалении участок пуст, ожидаемые marks — `[]`. Поздняя правка человека в целевом блоке даёт `verify(current).outcome = failed`, а `verify(at_commit)` той же квитанции остаётся `passed`.
  Это правило целого блока действует для документа в режиме snapshot. Для документа в режиме journal CRDT сводит конкурентные правки посимвольно: офлайн «15 → 20» и команда агента «15 → 30» дают «2030» или «3020», а не конфликт. Поэтому при commit владелец сохраняет в evidence квитанции два относительных положения Yjs вокруг заменённого участка, расширенного на один соседний символ с каждой стороны. `text_exact` в режиме `current` разрешает их в текущем состоянии. Проверка проходит, только если это окно читается так же, как при commit; `actual` — текущее окно. Вставка внутри участка или вплотную к нему и удаление участка или соседей проваливают проверку. Правка в другом месте того же блока её не проваливает. Якоря только по самому участку недостаточны: «30» остаётся «30» рядом со вставленным «20». **Книга.** `sheet.fill_formula@1` принимает ровно `{sheet_id,table_id,scope,destination_column_id,expression}`. В первой реализации `expression = {op:"subtract",left_column_id,right_column_id}`. Это типизированная операция разности значений в той же строке. Адаптер строит формулу движка по текущим координатам. Текст пользователя и формула имеют разные типы. Доступ и исходные значения обеих колонок, выходные ячейки и членство проверяются перед записью.

| scope | Как трактуется вставка строки между prepare и commit |
| --- | --- |
| `fixed_members` | Заполняются только устойчивые ID строк из прочитанной области. При сохранности этих строк, значений и выходных ячеек окружение может измениться. В фикстуре агент читает две из трёх исходных строк. После вставки между выбранными строками формулы идут в D2 и D4. Новая строка D3 остаётся пустой, исходная невыбранная строка сохраняет прежнее значение в D5. Если одну из выбранных строк удалили, результат — конфликт |
| `current_rows` | Поручение охватывает состав всей именованной таблицы, зафиксированный при подготовке. Изменившийся состав даёт `scope_changed`. Новое чтение, подготовка и новый ключ команды могут включить вставленную строку. Возобновление старого поручения использует прежний список |

Профиль проверки `formula_and_values` сопоставляет ID строк, сохранённые формулы и ссылки, рассчитанные значения и позицию завершённого расчёта. Только после этого вычисляется ожидаемый итог. Один и тот же ноль можно получить обратным знаком обеих формул или заменой формул константами, поэтому одного агрегата недостаточно. Обе команды действуют в пределах одного ресурса; связанная группа целей применяется целиком. Изменения между документами потребуют явных отдельных квитанций.

Для `outcome=passed` владелец берёт профиль из предложения, связанного с квитанцией. У `text_and_marks` ответ содержит ровно по одной проверке `text_exact` и `marks`. У `formula_and_values` обязательны `row_ids`, `formulas`, `calculated_values`, `calculated_at` и `sum`, каждое имя встречается один раз. Порядок проверок произвольный. Порядок внутри трёх массивов общий и соответствует целям предложения. Владелец сверяет длины, каждую формулу, её вычисленное числовое значение и маркер расчёта до выдачи успешного ответа. Схема проверяет форму одного ответа. Адаптер сверяет профиль с командой квитанции. Кроме того, адаптер отвергает ответ, допустимый по схеме, если `receipt_id` чужой, маркер `at_commit` не равен маркеру квитанции, `calculated_at` устарел, формулы или значения не соответствуют строкам в порядке целей (перестановка с той же суммой тоже отвергается), а `text_exact`/`marks` расходятся с согласованной заменой. Негативы: `adapter_negatives` в [verify-sdk-vectors.py](../scripts/ci/verify-sdk-vectors.py) и `scripts/ci/verify-sdk-vectors.py`.

## Предложение, запись и восстановление

1. Хост создаёт доверенный контекст с организацией, субъектом, проектом/доступным диском и разрешениями. При чтении сервер сохраняет или удостоверяет область, маркер, смысловые зависимости, схему и срок жизни `read_token`. Строка токена не является правом доступа. Повторное чтение только что изменённого блока с новой целью порождает новый токен.
2. При подготовке сервер разрешает цели и фиксирует неизменяемую запись предложения, версии команд, привязку к области пользователя, набор зависимостей, область и контрольную сводку. Клиент получает `proposal_id` и `digest` из 64 строчных hex-символов. Для воспроизводимой фикстуры digest вычислен как SHA-256 UTF-8 канонического JSON объекта `{version:1,prepare_input:<input>,plan:<result без digest>}` с упорядоченными ключами по JCS. Сервер сохраняет исходную запись по идентификатору, включая внутренние данные; клиент может лишь сослаться на неё. Хеш не служит секретом. В проекте с согласованием человек подтверждает конкретный digest через доверенный интерфейс. Смена предложения, важного пользовательского условия, истечение срока или отзыв права требуют повторной проверки.

   Канонизация — RFC 8785 без отступлений. Ключи упорядочиваются по кодовым единицам UTF-16: `😀` (D83D DE00) идёт раньше U+E000 и U+FB33. Порядок по code points или байтам UTF-8 (Python `sort_keys`, PHP `ksort`/`strcmp`) здесь ошибается. Экранируются только `"`, `\` и U+0000..U+001F: короткие формы `\b \t \n \f \r`, остальные как `\u00xx` строчными. `/`, DEL, U+2028/U+2029 и не-ASCII остаются как есть. Строка с одиночным суррогатом отвергается. Профиль digest v1 допускает только числа, равные безопасному целому по значению: `27.0` записывается как `27`, `-0` как `0`. Дробь, значение за пределами ±(2^53−1), NaN и Infinity отвергаются, иначе Node (IEEE double) и PHP/Python (точные целые) дали бы разные байты для `9007199254740993`. PHP декодирует JSON в `stdClass`, чтобы `{}` и `{"0":…}` остались объектами. Digest покрывает каждое поле `prepare_input` и `plan` (включая `proposal_id`, `base`, `approval`, `summary`, `targets`, `expires_at`), кроме самого `digest`. Внутренние предусловия (узел, контекст блока, смещения UTF-16, marks с атрибутами, версия схемы, режим записи, поколение и `state_version`) в wire не входят. Они хранятся неизменяемо в `v_ai_proposal_payloads` по `proposal_id`, который входит в digest. При commit владелец заново вычисляет digest по сохранённой wire-части. Действующий `Vaulter\Documents\Content\ContentHasher` (ключ дедупликации autosave) и `mmccook/php-json-canonicalization-scheme` 1.0.0 для digest непригодны: первый даёт `\uXXXX`, `\/`, порядок байтов и `{}`→`[]`, второй экранирует U+2028 и форматирует `10.0` как `1`. [Векторы](../tests/Fixtures/proposal-digest-vectors.json) · `python3 scripts/ci/verify-sdk-vectors.py`.
3. Хост сохраняет `command_id` до первой отправки. Уникальность задаёт кортеж `(tenant_id, project_scope, effective_subject, resource_id, command_id)`. Хост берёт постоянный идентификатор области проекта из удостоверенного контекста. У хоста без отдельных проектов одна постоянная область на организацию. Тот же ключ внутри области обозначает один исходный план. Перенос задания в другой проект требует нового разрешения субъекта, чтения и предложения. Предыдущее предложение, токен и квитанцию разрешают только в их исходной области. Фиксация сравнивает ключ, его неизменяемый fingerprint, текущие права, поколение, схему, целевой фрагмент и версии, использует штатный путь записи владельца. Для одиночного документа адаптер строит изменение от свежего состояния и выполняет условную запись; в случае гонки перепроверяет те же зависимости. Слепая замена старого полного JSON недопустима. Для живого документа владелец должен связать ключ с точными байтами принятого обновления и квитанцией. Политика PHP-операций должна отличать бизнес-команду агента от существующего REST autosave.
4. Если фиксация продолжается, `status` возвращает running. Подтверждённый повтор возвращает исходную квитанцию; проверка актуальных прав обязательна. Использование того же ключа для другого плана даёт `idempotency_conflict`. После потери HTTP-ответа клиент запрашивает `status`; при необходимости повторяет ровно прежний commit с сохранённым ключом, пока действует документированное окно дедупликации. Старый истёкший ключ не запускает новую запись. Квитанция и запись, достаточная для распознавания истёкшего ключа, имеют согласованную политику удержания. После неизвестного исхода за пределами этого окна требуется новое чтение и сверка истории до нового намерения.
5. Поручение исполняется от имени исходного инициатора. Права рецензента ограничены принятием решения и просмотром разрешённых ему данных. Хост проверяет право рецензента на согласование и отдельно актуальные права инициатора на каждом изменении. Единственность решения по предложению и порядок чтения квитанции описаны в [интеграциях хоста](host-integrations.md).
6. Независимый verifier читает сохранённый результат от владельца ресурса, привязывает проверку к квитанции и версиям контента/расчёта. При расхождении возвращает `outcome=failed` и только разрешённые фактические значения. При потере истории или истёкшем сроке доказательства выдаётся `evidence_unavailable`. Это не разрешает повторно запускать исходную мутацию.

Владелец подтверждает сохранение один раз. В случае разных процессов PHP/Node отметка «удалось» в AI-таблице отдельно от эффекта в журнале оставляет окно повторной вставки. Для живой комнаты требуется проверка всех источников записи (включая браузеры), восстановление подтверждённых байтов после падения и ограждение старого поколения. [Действующий путь записи Documents](../../packages/documents/src/Operations/DocumentOperations.php) · [Политики операций](../../packages/documents/src/Operations/DocumentsOperationPolicies.php) · [Фиксация и восстановление живой записи](collaboration.md)

### Ошибки и поведение клиента

`error = {code,retryable:boolean,next_action}`. Технические сведения, SQL, пути, токены, невидимые названия, чужой diff и подсказки по существованию объекта остаются на сервере. Унификация ошибок доступа применяется к поиску, чтению, статусу и проверке. Повторяемость относится к безопасному действию в последней колонке, а не к созданию новой команды.

| HTTP | code | retryable / next_action |
| --- | --- | --- |
| 400 | `invalid_input`, `unsupported_version` | false / stop |
| 401 | `authentication_required` | false / stop |
| 404 | `resource_unavailable` для невидимой либо скрытой цели; `operation_unknown` в авторизованном ресурсе | false / stop; для неизвестного ключа внутри окна — true / retry_same |
| 409 | `precondition_failed`, `scope_changed`, `generation_changed`, `schema_changed` | false / reread |
| 409 | `idempotency_conflict` | false / stop |
| 409 | `approval_required` | false / await_approval |
| 409 | `projection_pending`, `calculation_pending` | true / retry_read |
| 410 | `proposal_expired`, `cursor_expired`, `read_token_expired` | false / reread |
| 410 | `evidence_unavailable`, `idempotency_window_expired` | false / inspect_history |
| 413/422 | `limit_exceeded` / `unsupported_content` | false / narrow либо false / stop соответственно |
| 503 | `temporarily_unavailable` | true / status для записи, true / retry_read для чтения |

Ошибка дескриптора команды, которую хост не публикует этому субъекту, также возвращает `resource_unavailable`. Сбой транспорта без распознаваемого ответа трактуется как неизвестный исход. Сервис не обещает, что брошенное PHP-исключение соответствует откату изменений в другом процессе.

Для реализации маркеров и команд используйте спецификации владельцев. [Хранение и проекции](storage.md) · [Совместная запись](collaboration.md) · [Табличные книги](spreadsheets.md)

## Адаптеры и конфигурация

Состав продуктов, ограничение профилей и настройка интеграций описаны отдельно. [Интеграции хостов](host-integrations.md)

**Laravel AI в первом релизе (`laravel/ai ^1.3.0`, MIT).** Агент реализует `HasTools::tools()`; зарегистрированный `Tool` (`Laravel\Ai\Contracts\Tool`) объявляет `description()`, `schema(JsonSchema $schema)` и `handle(Request $request)` и передаёт запрос в офисный прикладной порт. Инструкции, модель, ссылка на секрет, лимиты шага и трат принадлежат профилю хоста. **Критическое ограничение `laravel/ai v1.3.0` (баг `#1206`):** встроенный Human Tool Approval срабатывает только для инструментов верхнеуровневого агента и может обходиться субагентами — поэтому `office.commit` обязан независимо проверять наличие подписанного человеком решения `P/Q` в БД владельца (возвращая `403` при отсутствии). Опциональный стабильный workflow-адаптер — `neuron-core/neuron-ai ^2.8.11` (MIT; нестабильный pre-1.0 `prism-php/prism` не рекомендуется). Обязательные проверки — фиктивный LLM, негативный тест вызова `office.commit` субагентом без P/Q и один настоящий прогон с разрешённой моделью. [Laravel AI SDK](https://laravel.com/framework/docs/13.x/ai-sdk)

**AgenTools опционально.** Локальный `agentools/sdk` содержит `AgenTools\Contracts\ToolPort::call(string $tool, array $arguments, string $idempotencyKey): ToolExecutionResult`, `ToolDescriptorRegistry::descriptor()` и `LlmPort::respond()`. Приватный мост в AI получает контекст хоста при создании, преобразует дескрипторы и ответы в формат AgenTools. Для commit стабильный ключ вызова пригоден как `command_id` только при подтверждённой стабильности в повторе; иначе мост извлекает ранее сохранённое соответствие из записи запуска. Каждый повторный planning run не генерирует новый ключ автоматически для уже принятой команды. `LlmPort` выбирается исполнителем независимо от офисных обработчиков. В наборах Edufy `apps/ai` и `modules/ai/AiCore` уже заявлены `agentools/sdk` и `agentools/platform-core` — это проверено по манифестам; подключение офисного моста ещё предстоит. Для другого хоста установка AgenTools необязательна. Браузерный агент и фоновое задание должны получить идентичные ACL и одно доказательство результата.

**Python и будущий интерактивный интерфейс.** Python-клиент сериализует те же сообщения поверх HTTP и повторяет ключ только в пределах исходного намерения. Для прохождения contract-тестов достаточно стандартного HTTP-клиента и JSON, отдельная ORM, Node или Python SDK в CMS не нужны. Loqum в экосистеме описан как платформа голосового сеанса (Python/LiveKit и TS-клиент). Позже его runtime сможет вызывать офисный API под ограниченным контекстом хоста, передавать поручение и озвучивать краткий проверенный результат. Первому релизу достаточно текстового поручения. Повтор события реплики после reconnect не создаёт второго `command_id`; прерывание речи не откатывает принятую правку. Если требуется согласование, UI показывает digest и разницу, выдаёт решение только через доверенный обработчик.

**Регистрация.** Хост подключает приватный компонент через свой Laravel provider. Для каждой команды регистрирует уникальные имя и версию, поддерживаемые типы документов, схемы входа и результатов, требуемую способность, проверяющий обработчик и владельца записи. Совпадающие имена и несовместимые реализации выявляются при загрузке. Владелец команды возвращает строго контролируемый план и регистрируемую проверку. Инструкции внешнего агента могут только сужать доступный набор. Разные модели используют одну версию офисной команды без конвертации содержимого между PHP, TS и Python.

## Сценарии приёмки

[Файл обменов](../examples/office-sdk.json) — примеры для контрактных тестов будущих PHP/HTTP- и Python-адаптеров. Каждый сценарий независим. Массив `events` описывает действия стенда за пределами wire-сообщений. Поле `before_step` начинается с 1, события с одинаковым номером выполняются в порядке массива непосредственно перед этим запросом. Событие `drop_next_response` настраивает транспорт на потерю результата ближайшего вызова после фиксации владельцем. Поле `response` пары в таком случае описывает исход у сервера. Вызывающий видит только разрыв.

| Сценарий | Условие и проверка |
| --- | --- |
| `text_success` | Получить ID договора поиском, найти p42 в оглавлении. До commit сотрудник исправил p71, увеличив позицию с 27 до 28. Команда сохраняет 30 с прежним полужирным оформлением на 29. Чужая правка видна отдельным чтением p71 после квитанции |
| `sheet_fixed_members` | Из трёх строк явно выбраны две со значениями +20 и −20. Человек вставил строку 40/55 перед второй выбранной после prepare. SDK записывает формулы в ставшие несмежными строки и проверяет состав и сумму 0. Стенд проверяет также пустую D3 и прежнее значение 77 в D5 |
| `sheet_current_rows` | Та же вставка инвалидирует digest по составу. Первый commit возвращает конфликт. Новое чтение и предложение изменяют три строки с новым ключом; результат +20, +15, −20 и 15 |
| `lost_response` | Стенд скрывает первый ответ commit от вызывающей стороны, хотя владелец завершил транзакцию. Status и повтор идентичного commit возвращают ту же квитанцию и позицию. История владельца содержит один эффект |
| `acl_revoked` | Между prepare и commit отозваны чтение и запись. И commit, и status скрывают существование объекта. Отдельные тесты отзыва только записи и только права просматривать историю проверяют предусмотренное хостом разделение |
| `text_conflict` | После read сотрудник изменил «рабочих» на «календарных» в p42. Атрибуты исходного фрагмента и его смысловые зависимости переоцениваются. Запись отклонена, содержимое сотрудника сохранено |

Следующая группа испытаний проверяет конкурентные повторы одного ключа, иной payload под тем же ключом, истёкшее предложение, подмену токена другого tenant, два решения accept/reject, прекращение задания и поздний голосовой retry. Для живой комнаты нужны падение после журналирования до применения, поздний update отключённого устройства, восстановление с новым поколением и проверка двух разных ветвей `at_commit/current`. Для книг отдельно вводится ложный кэш расчёта, скрытая строка или удаление именованной области. Измерение ресурсов сравнивает адресные вызовы и полный снимок при одинаковых правах и одинаковом эталоне. Учитываются описания инструментов в prompt, байты ответа, реальные чтения PostgreSQL/блобов, длительность, память и правильность результата.

## Границы первого профиля и последующее расширение

Для сравнения реализаций задать в тестовом хосте одинаковый профиль: первая страница поиска до 5 ресурсов, целевое чтение до 20 строк и до 16 КиБ сериализованного ответа, максимум 20 строк на одно предложение. Это параметры стенда. В продуктовой конфигурации их можно менять по результатам замеров. При лимите 2 проверить таблицу из 3 строк: адресный выбор двух доступен, выбор всей таблицы за одну страницу не помещается, его усечение не даёт права молча применить изменение к двум строкам. Для слишком большого одиночного значения вернуть предусмотренный отказ с предложением сузить запрос. Сверять число байтов UTF-8 и фактически полученные токены провайдера раздельно.

Когда результат команды зависит от выходной ячейки, которую агент не просил показать, владелец проверяет право записи и фиксирует её исходное содержимое при подготовке как внутреннее предусловие. Для выбранного столбца D в примере проверяются фактическое значение или формула и её версия у каждой цели. Человеческая правка D2 после prepare вызывает конфликт. Ячейка D5 вне области сохраняет 77. Если нельзя безопасно подготовить или показать человеку разницу в пределах его прав, предложение не исполняется.

Для следующих поставок офисного SDK добавлять по одной пользовательской операции через существующие доменные входы. Первая схема wire ограничена двумя командами. Новая возможность получает версионированный дескриптор и согласованное расширение схемы; уже зарегистрированное задание досматривает свою зафиксированную версию каталога.
