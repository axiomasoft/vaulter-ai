## Идентичность и хранение данных

Логический ключ команды — `(tenant_id, project_scope, effective_subject, resource_id, command_id)`. В Core идентификаторы доменов приходят от разных процессов и сравниваются как непрозрачные строки с точным регистром. Локальный reference-профиль владельца преобразует tenant в bigint. Для одноарендной установки нужна одна постоянная область, привязанная конфигурацией к этому endpoint. Адаптер субъекта кодирует тип и ключ principal однозначно, например `user/42` или `service/42`. Значения из HTTP body не определяют область. CHECK ограничивает компоненты составных B-tree ключей в байтах, в том числе многобайтный UTF-8. Для тестов, где wire ID вида `contract-17`, backend fixture ведёт явное соответствие реальному UUID узла и реальному субъекту. Обратное преобразование wire-идентификаторов выполняет доверенный адаптер.

Внешний `resource_id` документа равен `v_nodes.id`. Внутренний `document_id` берётся через уникальный `v_documents.node_id` после авторизации. В SQL-профиле OWNER оба значения UUID, но представляют разные объекты; они совпадают только случайно. `v_ai_text_commands.document_id` использует FK с SET NULL, чтобы после удаления документа сохранился маркер использованного ключа. `resource_id` в этой записи долговечен. Сборки и абзацы имеют FK к документу с CASCADE. На независимом Core соединении FK к внутренним таблицам владельца отсутствуют. При выпуске Laravel-пакета типы ссылок и tenant выбирают по настройкам Vaulter. Контрольные установки повторить на ULID и bigint с одной стратегией во всех зависимых пакетах. [Владелец ID](../../../docs/adr/0011-id-strategy.md)

Хеши и digest в SQL — бинарные 32 байта; wire выдаёт digest 64 строчных hex-символами. Для проверки сериализации используется каноническое представление подготовленного объекта по JCS из Office SDK. В `request_fingerprint` участвуют версия команды, привязанный proposal_id и digest; сравнение выполняется внутри области одного ключа. Значимые предусловия, тип документа и выбранный писатель фиксируются в неизменяемом плане. `key_id` указывает на ключ зарегистрированного хостом authenticated-encryption codec. Ciphertext включает версию, nonce и authentication tag. AAD связывает таблицу, ID записи и область. В обычном логе отсутствуют исходные фрагменты, секреты провайдера, скопированное содержание книги и полный запрос модели. Форматированные абзацы для поиска являются разрешённой серверной проекцией с теми же проверками доступа, сроками хранения и удалением, что и канон.

## Существенные транзакции и граничные случаи

1. **Чтение и сохранение read_token.** Сервис проверяет доступ и маркер источника, фиксирует publisher snapshot и scope; затем выпускает токен со сроком. На каждом использовании повторно проверяет scope, ACL, полноту, назначение selector и версии. Для собственной конфигурации стенда задать TTL чтения/курсов 15 минут, TTL предложения 1 час; в fixture с явно заданным expires_at использовать её clock и срок. За пределами доверенной области возвращать ответ скрытого ресурса. Срок жизни и секрет не предоставляют полномочий.
2. **Решение человека.** Предложение P выбирается в доверенной области с блокировкой строки. Условное обновление разрешает переход только из pending. При принятии сначала зарегистрировать route с уникальным ключом и писателем и один dispatch в той же транзакции. При отклонении commit и dispatch отсутствуют. На автоматическом пути связать route с P при первом разрешённом commit после проверки срока. Существующий route и тот же fingerprint возвращают сохранённый исход при наличии текущего доступа. Конфликтную запись с новым ключом/старым P не ставить в очередь. Аудируемая привязка reviewer доступна отдельно от effective_subject. Смена политики до исполнения требует актуального разрешения. Строгий профиль проверяет действующее согласие у владельца, в одной локальной транзакции с записью. Если authoritative согласие живёт в другом сервисе и нельзя доказать его действительность в момент фиксации, данный отдалённый писатель в таком профиле недоступен.
3. **Фиксация и возврат пользователю.** Три отдельных commit, без транзакции между соединениями. #1 CORE: route (ключ, proposal_id, fingerprint, `owner_key` из запечатанного плана) до вызова владельца. #2 OWNER через AtomicDocumentMutation: T → N → решение Edit на заблокированном узле → D; исход по ключу или proposal_id → при наличии сверить fingerprint и вернуть сохранённое без проверки режима и поколения; иначе проверить поколение, режим, схему и исходный смысл цели. При новом эффекте сохранить изменённый канон, квитанцию, evidence и доменное событие. Откат любого из них откатывает всё; callback может повториться после 40001/40P01. Предсказуемый конфликт цели сохранить как rejected без изменения документа. #3 CORE: `receipt_id` в route, затем ответ клиенту. Отзыв доступа выдаётся по текущим правам даже при ранее успешном результате; существование квитанции не просачивается через код ответа. Если процесс умер между #2 и #3, тот же status или commit по ключу идёт к `owner_key` из route, восстанавливает уже зафиксированную квитанцию, заполняет locator и лишь тогда отвечает. Уникальность по scope и fingerprint защищает от второго эффекта. Изменение текущего режима редактора не меняет владельца старой квитанции. В `v_ai_text_commands` пары `source_generation/source_position` — это маркер документа **после** записи, то есть маркер квитанции (в `lost_response` это 3/29 при base 27). Исполняемая проверка — `the atomic-mutation integration check`.
4. **Отдача исторического результата.** Выбрать route по scope + receipt_id, проверить актуальные права на узел/историю, разрешить квитанцию и прочитать evidence у владельца. Для current сверить поколение и позицию фактического чтения. Для at_commit сравнить сохранённый фрагмент и постусловия. При потере evidence вернуть evidence_unavailable; отсутствие/удаление ресурса с отсутствием доступа выдаёт resource_unavailable. Для тестового профиля сохранить доказательство 24 часа и окно повтора 7 дней; число задаётся конфигурацией стенда, в продуктовой поставке владелец политики задаёт срок по данным пользователя.
5. **Перестройка проекции.** Из согласованного source snapshot собрать ограниченное или полное новое дерево, запретить повтор block_id. В транзакции сравнить текущий источник/поколение и опубликованный head, вставить согласованные строки и установить указатель через CAS. Для больших документов возможны порции в новом build_id: pointer переключать после завершения всей сборки, предварительно повторно сверив источник. После разрыва доставки дочитать недостающий участок или rebuild. При переходе на новое поколение старый worker прекращает работу. Один ответ читает head и строки единым SELECT, либо в одной транзакции уровня REPEATABLE READ.
6. **Очистка и восстановление.** Извлекать порциями записи с истёкшими индексированными сроками. Сначала останавливать выдачу, затем удалять ciphertext и расцеплять внешние артефакты по политике. Старые сборки чистить только при отсутствии активного builder/путём локальной сериализации по документу и после перепроверки head. Для многошаговой сборки выделить собственный advisory lock при записи и уборке, одинаковый для этого документа. Удаление шагов, выборок и payload идемпотентно. За окном повторов ключ не запускается снова: компактный route/command tombstone остаётся до ликвидации namespace; на старый ключ с тем же намерением — 410. Для удаления всей области удалить зависимые dispatches и routes, затем предложения и runs только после остановки всех её исполнителей и отзыва доступа/очередей. Если утрачены доменные данные или недостижим владелец, outcome требует сверки по прежнему ключу; новый ключ без выяснения исхода не создаётся.

## Приёмка схемы

| Упражнение | Ожидаемый результат |
| --- | --- |
| Создать в CORE две организации с одинаковым command_id и локальным resource_id; затем под одним scope повторить key с другим digest | У организаций независимые записи; конфликт в одной области остановлен. Композитный FK отвергает ссылку на предложение другого субъекта |
| Принять/отклонить один P в двух PostgreSQL-сессиях; попытаться выдать два command_id на P; удалить P при родительской привязке | Одно решение и не более одного route/dispatch. Вторая связка отвергается UNIQUE, удаление используемого P — RESTRICT |
| После потери ответа повторить регистрацию ключа, затем очистить evidence, затем истечь dedupe_window | До истечения один эффект и та же квитанция; после удаления доказательства at_commit даёт 410; после окна фиксация прежнего ключа даёт idempotency_window_expired. Контент не изменён повторно |
| Удалить SearchPage, Run и Document на выделенном стенде | Состав снимка и шаги/исходный запрос удалены своими CASCADE; проекции удалены по локальному document_id. Tombstone команды хранит внешний resource_id и NULL внутренний FK, без возможности выдачи доказательства удалённого ресурса |
| Запустить тот же набор на одном соединении и с отдельной БД вызывающего процесса | В каждом профиле marker, квитанция, ACL и итог однотипны. Возврат committed невозможен при потере атомарной связи эффекта с исходом |

На PostgreSQL 18.4 выполнен smoke со свежей установкой Core/Media/Drive/Documents и обоих AI DDL. Проверены все 14 новых таблиц, отказ ручного согласования без reviewer, защита чужого scope, две независимые организации, запрет второго ключа по P, UNIQUE команды у владельца и раздельная очистка доказательства, проекции и использованного ключа. Тест создаёт строки во временной транзакции и завершает её ROLLBACK. Для повторения на отдельной тестовой БД с загруженными определениями выполнить `psql -X -v ON_ERROR_STOP=1 -f scripts/ci/sql/ai-checks.sql`. Гонка двух физических соединений и перезапуск настоящего обработчика остаются проверками интеграции кода. На уровне SQL и PHP-образца их воспроизводит `the atomic-mutation integration check`: отдельные процессы, отдельные БД OWNER и CORE, барьер через `pg_blocking_pids`, kill после commit владельца.
